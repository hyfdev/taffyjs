# @taffyjs/node Decisions

This ledger records only judgments that Yunfei explicitly expressed about @taffyjs/node. Implementation, passing tests, review, or silence do not constitute acceptance.

## Decided

### Thin high-level TaffyTree binding

[VOUCHED @hyfdev 2026-08-09]

**Ruling:** @taffyjs/node must be a thin native binding to Taffy's high-level TaffyTree usage model. Thin means that layout state and implementation remain in Rust and Taffy, with no JavaScript shadow tree or reimplemented layout abstraction; it does not mean exposing Taffy's low-level traits, internal types, or every public Rust symbol. APIs aimed at greater performance or JavaScript ergonomics may be added alongside this baseline but must not replace it or make it depend on a higher-level JavaScript abstraction.

**Limits:** This decides the package's role and API priority, not the exact JavaScript names, object shapes, call granularity, type representations, ownership model, error mapping, callbacks, validation, conversion, copying, or batching strategy. Rust alignment means preserving the capabilities, concepts, semantics, and visible costs of Taffy's TaffyTree-centered layout usage as directly as Node.js permits. It does not mean reproducing every public symbol in the Rust crate. Higher-level product and compatibility designs remain outside @taffyjs/node. Necessary Node-API interop costs do not conflict with this ruling. Changing this direction requires a new explicit project decision.

**Why:** @taffyjs/node is the foundation that guarantees access to Taffy without requiring consumers to adopt an additional JavaScript-side design. Keeping this path direct follows a zero-cost-abstraction principle: consumers should not pay for an optional higher-level wrapper they do not use. A direct surface is intentional at this layer, while proven performance or experience improvements can still be offered as additions.

**Source:** Yunfei (`@hyfdev`), 2026-08-09; explicitly confirmed the direct binding direction, clarified that Rust alignment applies to Taffy's high-level layout usage rather than complete crate symbol coverage, and vouched the thin high-level native binding wording.

### Safe and sound JavaScript boundary

[VOUCHED @hyfdev 2026-08-10]

**Ruling:** Safety and soundness are the binding's second design priority, immediately after preserving Taffy's high-level semantics. Every supported @taffyjs/node API path must validate values, node identities, ownership, lifetime, and operation preconditions before they can violate a Rust or Taffy invariant. Invalid use of @taffyjs/node and expected Taffy failures must produce controlled JavaScript errors rather than Rust panics, internal errors, invalid aliasing, or undefined behavior. Direct imports or calls to @taffyjs/binding-<platform> packages are unsupported implementation access and are outside this public safety contract.

**Limits:** This ruling does not choose the JavaScript error classes for cases not decided separately, validation for non-node values, or panic-containment mechanism. The platform packages remain loadable npm dependencies because the maintained napi-rs loader needs them, but their raw exports must not be re-exported as supported @taffyjs/node operations. This ruling does not claim that the binding can prevent process termination caused by allocation failure, an aborting dependency, direct unsupported platform-package use, or an unknown upstream defect. Panic containment may be a defensive backstop, but it must not replace validation and typed error handling on the supported @taffyjs/node paths.

**Why:** JavaScript callers can freely construct malformed values, retain stale NodeIds, mix NodeIds from different trees, and re-enter callbacks. The public boundary must make those cases safe and predictable before they reach native code whose invariants assume valid Rust values and relationships.

**Source:** Yunfei (`@hyfdev`), 2026-08-09 and 2026-08-10; explicitly made safe and sound JavaScript behavior the second design principle, required the supported @taffyjs/node API to prevent JavaScript misuse from producing panics or internal errors, and explicitly excluded direct @taffyjs/binding-<platform> use from that guarantee.

### Taffy-owned semantic behavior

[VOUCHED @hyfdev 2026-08-11]

**Ruling:** Once @taffyjs/node has mapped an ordinary JavaScript input unambiguously into the selected Rust value, satisfied the binding's explicit identity, ownership, lifetime, absence, and complete-update semantics, and excluded a known panic or native-safety violation, it must pass that value to Taffy and expose Taffy's resulting state, output, or typed error. The baseline binding must not add JavaScript-side semantic range checks, clamping, normalization, or default substitution merely because a Rust-representable value is unusual or may produce an unhelpful layout. This is the default for later API mappings as well as Style.

**Limits:** The boundary must still reject JavaScript types and shapes that cannot map to the selected Rust API, unsupported variants and fields, malformed binding-owned identities, and inputs known to reach a Taffy panic, undefined behavior, native-state corruption, or disagreement between binding-owned and native state. Explicitly vouched JavaScript contracts such as NodeId ownership, Style absence semantics, closed-enum membership, complete conversion before mutation, and callback lifetime remain in force. A safe Taffy-provided error should normally be translated rather than reimplemented through duplicate JavaScript validation. Behavior outside Taffy's documented semantic domain follows the pinned Taffy version and is not a separate taffyjs compatibility promise. Yoga demonstrates a similar responsibility split but does not define taffyjs normalization details.

**Why:** @taffyjs/node is the direct Taffy binding, so JavaScript should not silently become a second layout-policy layer. Values that Rust and Taffy can safely receive belong to Taffy's behavior even when callers can obtain surprising results. Boundary work is justified when JavaScript cannot express the Rust invariant by construction or when forwarding would threaten process or state safety, not solely to make every caller-supplied value sensible.

**Source:** Yunfei (`@hyfdev`), 2026-08-11; explicitly said that setStyle should map JavaScript values into representable Rust values and otherwise follow Taffy's `set_style` behavior, approved passing negative and non-finite floating-point values without JavaScript-side defense, and generalized the same default to future API design while retaining prevention of panics.

### High-level layout-engine scope

[VOUCHED @hyfdev 2026-08-09]

**Ruling:** @taffyjs/node must bind Taffy's TaffyTree-centered high-level layout-engine usage surface. It must expose what JavaScript consumers need to construct and mutate layout trees, provide styles and measurements, compute layouts, and read results; it must not pursue symbol-for-symbol coverage of Taffy's Rust crate.

**Limits:** The comparison to yoga-layout describes the package boundary and intended completeness of normal layout usage, not a requirement to copy Yoga's API shape. A Yoga-compatible API remains the responsibility of @taffyjs/node-yoga. Taffy's low-level custom-tree traits, trait-dependent single-algorithm compute functions, cache internals, helper traits, and generic implementation infrastructure are outside the default binding scope. A JavaScript-owned custom tree or other low-level algorithm adapter requires a new explicit direction. The exact high-level methods and transitive value types still require systematic mapping.

**Why:** The package is a usable binding for performing layout from JavaScript, not a mirror of every Rust implementation and extension mechanism. Limiting the surface to Taffy's own high-level usage keeps the binding direct while avoiding APIs whose Rust abstraction and cost model do not carry across Node-API.

**Source:** Yunfei (`@hyfdev`), 2026-08-09; explicitly confirmed that @taffyjs/node should resemble yoga-layout in binding the usable layout API rather than mapping every Rust detail, and approved this interpretation as a project decision.

### Binding design principles

[VOUCHED @hyfdev 2026-08-10]

**Ruling:** The binding must preserve Taffy's high-level Rust semantics and capabilities without mechanically copying Rust syntax; Rust and Taffy must remain the only source of tree, style, layout, and computation state, while JavaScript may keep private identity and validation metadata that does not mirror that state; implicit costs such as deep copies, object conversion, callbacks across the language boundary, and per-node calls must be treated deliberately; the direct baseline API must remain available when additive batch or higher-performance APIs are introduced; ownership, node validity, cross-tree misuse, and error behavior must be explicit; and Yoga compatibility, reactive objects, and other higher-level designs must live in @taffyjs/node-yoga or another package above @taffyjs/node.

**Limits:** Binding metadata may identify the tree that issued a NodeId, associate a current Taffy NodeId with a binding-issued serial, and reject stale or foreign NodeIds. It must not become an authoritative JavaScript copy of parent, children, Style, Layout, cache, or other Taffy state. These principles do not otherwise decide the concrete JavaScript API, names, value representations, callback interface, batching shape, or which optimizations are worthwhile. They also do not require eliminating unavoidable Node-API conversion costs. Those choices must be evaluated from the Rust model, napi-rs's available representations, and measured consumer needs.

**Why:** @taffyjs/node is the direct foundation for other JavaScript APIs. Its state ownership, costs, and failure boundaries therefore need to remain visible and predictable, while optional convenience and performance paths must not make the direct binding unavailable.

**Source:** Yunfei (`@hyfdev`), 2026-08-09 and 2026-08-10; explicitly approved these binding principles before concrete API design and later approved a private JavaScript NodeId registry while keeping Taffy's actual tree and layout state native.

### Ordinary data-object default

[VOUCHED @hyfdev 2026-08-11]

**Ruling:** Unless a concrete boundary has special semantics or evidence requiring another representation, JavaScript record-shaped inputs must be designed under ordinary data-object assumptions rather than around side effects from getters or Proxy traps. A tagged-union branch must declare its discriminator and the payload fields it requires, but must not add optional-`never` properties solely to emulate exact object types by excluding fields used by other branches. Runtime conversion selects the discriminator and reads that variant's required payload; it must not add pairwise checks for other variants' payload fields solely to compensate for TypeScript structural assignability.

**Limits:** Unknown discriminators and missing or incorrectly typed required payloads still fail conversion, and explicitly selected unknown-field policies such as the Style and partial-geometry rules remain in force. A payload field used by another variant may be rejected later only when its presence makes conversion ambiguous or threatens safety, not merely because TypeScript may retain an extra structural property. A Rust ownership or lifetime requirement, an explicit callback, retained JavaScript state, a distinct public grammar, measured conversion cost, or another concrete constraint may justify a native wrapper, preprocessing, or other special representation. Such a case must state the reason instead of treating unusual property access as the general baseline.

**Why:** Yunfei wants ordinary application data to set the default complexity budget. Supporting unlikely accessor- or Proxy-driven behavior by default would make common paths and future mapping rules harder to understand without a demonstrated consumer need. Optional-`never` exclusions grow with every mutually exclusive payload field and add declaration noise to protect a structural-typing edge case that the caller can avoid.

**Source:** Yunfei (`@hyfdev`), 2026-08-11; generalized the Style correction into a binding-wide default and said ordinary cases should assume ordinary data objects unless a special case is identified; later rejected optional-`never` payload exclusions as overdesign and made structural extra-field typing the caller's responsibility.

### Readonly output declarations and mutable input records

[VOUCHED @hyfdev 2026-08-11]

**Ruling:** Binding-produced record snapshots must expose readonly properties in their TypeScript types because mutating those records cannot change Taffy state and normally expresses a mistaken intent. Record-shaped input types must not declare their properties readonly; callers may create and mutate ordinary JavaScript objects before passing them. Input conversion must use ordinary property access without detecting, rejecting, copying, freezing, or adding repeated checks solely because an object may contain accessors or be a Proxy; those behaviors and side effects are caller intent and responsibility.

**Limits:** TypeScript readonly is compile-time guidance and does not require `Object.freeze`, `Object.seal`, a Proxy, or another runtime mutation guard. Runtime representation and freezing remain cost decisions where already open. This rule applies to value-record inputs and owned record snapshots, not to primitive values or native owner classes whose methods intentionally mutate native state. Selected shape, variant, unknown-field, identity, and panic-safety rules still apply.

**Why:** Readonly output declarations prevent accidental code from implying that a detached snapshot is a live native view. Applying the same restriction to inputs would add friction without protecting native state, while special handling for accessors or Proxy traps would spend complexity on behavior the caller deliberately introduced.

**Source:** Yunfei (`@hyfdev`), 2026-08-11; explicitly required output snapshots to use readonly TypeScript types, rejected readonly input declarations, and generalized ordinary accessor and Proxy behavior as caller responsibility rather than a JavaScript-side defense target.

### Direct layout-state behavior

[VOUCHED @hyfdev 2026-08-09]

**Ruling:** The baseline JavaScript API must preserve Taffy's explicit computation and stored-layout behavior: reading layout returns the value currently stored by Taffy, including zero values before the first computation and previous results after inputs change; changing style or tree state must not compute layout automatically; returned Layout values must be owned snapshots with readonly TypeScript properties rather than live views into the tree; and, if Taffy's dirty-state query is exposed, it must retain Taffy's cache-state meaning without being presented as a guarantee that a node's stored layout is current. APIs that compute automatically or otherwise guarantee a current result may be added only as optional sugar.

**Limits:** This ruling does not decide whether the dirty-state query belongs in the public API, the names of any methods, or the shape of Layout values. Runtime sealing or freezing is an open representation and cost choice, not part of this decision. Failure-state layout validity and batch layout reads also remain open.

**Why:** @taffyjs/node is the direct Taffy binding and must not add automatic work or reinterpret Taffy's state by default. Yunfei explicitly accepted Taffy's zero-before-compute, old-value-until-recompute, borrowed-to-owned-copy, and cache-state semantics, while allowing separate sugar APIs when useful.

**Source:** Yunfei (`@hyfdev`), 2026-08-09; explicitly vouched the conclusions from the first four outer-layer mapping experiments.

### Direct layout-computation signatures

[VOUCHED @hyfdev 2026-08-10]

**Ruling:** The direct API must expose separate `computeLayout(options)` and `computeLayoutWithMeasure(options)` methods that preserve Taffy's `compute_layout` and `compute_layout_with_measure` semantics, use named option objects for their Rust-equivalent inputs, return `void` on success and throw controlled JavaScript errors on failure; the synchronous measure function must receive one owned readonly object containing `knownDimensions`, `availableSpace`, `node`, `context`, and `style`, and return a width-and-height size object. The selected TypeScript shape is recorded in [Taffy-to-Node binding mapping](binding-mapping.md#selected-layout-computation-signatures).

**Limits:** This decision fixes the two baseline methods, their named-object structure, and their direct semantic correspondence to Taffy. The concrete `AvailableSpace` representation is fixed by a later value-family decision; this decision does not itself fix the full Style representation, runtime freeze or seal behavior, whether a callback may replace context, callback-exception containment, or the native tree's reusable state after callback failure. `TaffyTree<TContext>` is a TypeScript-only context type and does not make Rust aware of the JavaScript value. A measured need may add a positional, batch, retained-callback, or other performance or convenience API, but it must not replace or silently change this direct path.

**Why:** These signatures retain the capabilities and explicit computation model of Taffy's two high-level methods. Named objects make the outer inputs and the five callback values harder to reorder or misread without adding automatic computation, tree access inside measurement, or another layout abstraction. Rust borrows become owned JavaScript boundary values, and Rust `Result<(), TaffyError>` becomes JavaScript's ordinary `void`-or-throw convention.

**Source:** Yunfei (`@hyfdev`), 2026-08-10; explicitly accepted the proposed `computeLayout` and `computeLayoutWithMeasure` TypeScript signatures as the direct Rust API mapping with named-object JavaScript ergonomics and asked that they be vouched.

### Value-based NodeId identity

[VOUCHED @hyfdev 2026-08-11]

**Ruling:** @taffyjs/node must expose node identity as an opaque-encoded JavaScript bigint named NodeId with a private TypeScript phantom marker named `phantomMarker` rather than as Taffy's raw `u64` or a JavaScript object. The value must combine enough private binding information to identify the issuing tree, the binding-issued identity of that node creation, and the corresponding raw Taffy NodeId. Repeated retrieval of the same current node must return the same bigint value, so `===`, `Map`, `Set`, and `includes` work without a native call. Each public TaffyTree wrapper must store its private native tree in `#inner` and use a private JavaScript current-node registry to check the bigint's form, tree identity, current binding-issued identity, and raw Taffy NodeId in expected constant time before synchronously calling native code. Each tree must generate an independent, cryptographically secure tree token of at least 128 bits; tree construction must fail if secure generation fails rather than falling back to a module-local counter. A NodeId is valid only for the exact TaffyTree that issued it and is not a persistent or transferable identity across workers or separately evaluated or installed package copies. This JavaScript registry is the sole NodeId-validity registry for the supported API; the initial native layer must not duplicate it or repeat the same owner and liveness check.

**Limits:** The TypeScript phantom marker only helps type checking; JavaScript can still construct arbitrary bigints, so every supported operation must perform the private runtime check. The exact bit layout, field widths, serial allocation, and error classes remain implementation choices, but the encoding must not expose the raw Taffy NodeId as the complete public identity or allow an old NodeId to become valid for a later node when Taffy reuses internal storage. The random tree token provides collision resistance rather than mathematical uniqueness; unsupported transfer does not gain persistence or interoperability semantics, but a target tree should reject a copied or foreign value through its ordinary runtime check. Removing a node deletes its registry entry, clearing a tree clears the registry, and collecting the tree collects the registry. Merely dropping a JavaScript NodeId does not remove its Taffy node or registry entry; explicit `remove`, `clear`, or collection of the whole tree owns that lifetime. A NodeId is a primitive and does not keep its tree alive. The validity guarantee applies to @taffyjs/node, not direct platform-package calls. The ordinary value-object path performs one current-node lookup immediately before its synchronous native call. It does not repeat that lookup after native argument conversion or create a dedicated defensive copy solely to handle tree mutation from a getter or Proxy trap; deliberate accessor- or Proxy-driven re-entry on the same tree is outside the initial contract. Complete ordinary value conversion before this operation mutates the tree remains required. Real consumer evidence, a normal supported operation that deliberately executes application code after the lookup, or a defense that becomes effectively free may reopen this boundary.

**Why:** JavaScript's built-in collections and strict equality can compare bigint values directly, while object-based node handles would require canonical object retention or a separate comparison API. Common tree operations need returned parents and children to work naturally in `Map`, `Set`, and `includes` without crossing the JavaScript-to-native boundary just to compare identity. The tree identity prevents cross-tree confusion, and the binding-issued identity ensures that reuse of a Taffy internal ID does not revive an old JavaScript NodeId. Keeping this check in the public JavaScript wrapper avoids a duplicate native registry while preserving controlled errors on every supported path. Getter- or Proxy-driven Style mutation is not an expected input pattern, and Yunfei judged the extra normalization or repeated lookup needed solely for it to be over-defensive.

**Source:** Yunfei (`@hyfdev`), 2026-08-10 and 2026-08-11; explicitly replaced the earlier External design after identifying ordinary `Map`, `Set`, `includes`, and `===` usage as a core requirement, chose a private composite bigint NodeId with JavaScript-side constant-time validation, required internal Taffy ID reuse not to change JavaScript identity guarantees, approved JS-only validation for the supported @taffyjs/node API, named the TypeScript marker `phantomMarker`, named the wrapper's private native field `#inner`, and approved an at-least-128-bit secure random per-tree token with tree-local, nonpersistent, and nontransferable NodeId semantics; later rejected a dedicated side-effect-free Style normalization boundary and repeated NodeId validation when their purpose was to defend against accessor or Proxy side effects.

### Style container semantics

[VOUCHED @hyfdev 2026-08-11]

**Ruling:** The baseline Style input must be an ordinary camelCase data object named `StyleInput`, with mutable TypeScript properties and every field optional. A missing field or explicit `undefined` must use that field's `Style::DEFAULT` value. Fixed-shape `Point`, `Size`, `Rect`, and `Line` records used directly as Style fields must also be partial input records: a missing or explicit-`undefined` component uses that component of the enclosing field's `Style::DEFAULT` value, while an unknown enumerable string component produces a controlled argument error. `null` must explicitly select no value only for a publicly nullable Style field, currently represented by Taffy as `Option<T>`, and must be rejected elsewhere. Every optional input property that accepts explicit `undefined` must include `| undefined` in its TypeScript declaration, and every property where `null` and `undefined` have different meanings must carry property-level JSDoc that states both meanings. Unknown enumerable string fields must produce a controlled argument error, and `setStyle` must construct and replace one complete Style rather than merge with the stored Style. Input conversion must not add special handling solely for accessors or Proxy traps. The public high-level Style vocabulary must not expose calc while `TaffyTree` resolves every calc pointer to zero and provides no resolver. The initial API must expose `getStyle(node)` as a read of Taffy's complete stored Style and return a complete independent `Style` snapshot whose TypeScript properties, including every fixed-shape nested component, are readonly and whose nullable Taffy values are concrete values or `null` for `None`, never missing or `undefined`. Case 2 records the current eager plain-object runtime baseline separately from these container semantics.

**Limits:** Missing and explicit `undefined` have the same input meaning, and conversion stores only the resulting complete Style rather than how the caller wrote it. Nested partial records fill from the corresponding enclosing Style default, never from the node's stored Style, and do not establish recursive omission semantics for tagged variants, grid payloads, arbitrary user objects, or other records without an unambiguous enclosing default. When a nullable field's Taffy default is `None`, missing, `undefined`, and `null` converge on the same stored value; if a nullable field's default is `Some(value)`, missing and `undefined` select that default while `null` still selects `None`. Property-level JSDoc must explain the distinction wherever both forms are accepted, even when the current default makes their stored results equal. Readonly output declarations do not imply a `Readonly` prefix in the public type name. The future non-grid field inventory is a mechanical derivation rather than an open API-design question; Cargo calc-feature configuration remains open. A future merge or patch API would define a different outer omission rule and requires a separate decision.

**Why:** Partial input mirrors Taffy's common `Style { selected_fields, ..Default::default() }` construction, while complete replacement preserves `TaffyTree::set_style`. Allowing a fixed-shape nested record to select only the components it changes gives JavaScript the same practical independence as per-component setters without turning `setStyle` into a merge with stored state. Missing and `undefined` retain ordinary optional-property behavior, while `null` gives a nullable field an explicit empty value that remains distinct if its default is nonempty. Writing `| undefined` keeps the declaration truthful under TypeScript's `exactOptionalPropertyTypes`, and property-level JSDoc makes the `null` and `undefined` meanings visible where users encounter the field. Returning `None` as `null` preserves the complete output shape and lets nullable output values be passed back as input. Rejecting unknown fields catches ordinary misspellings or unsupported layout properties instead of silently changing layout. Excluding calc avoids claiming support for a value the selected high-level tree cannot resolve. The measure callback may pay output conversion cost repeatedly, so later optimization still requires measurement even though it no longer blocks the initial representation.

**Source:** Yunfei (`@hyfdev`), 2026-08-11; accepted the proposed first Style checkpoint, then clarified that missing and `undefined` select the default, `null` explicitly selects `None` for nullable fields, complete output represents `None` as `null`, affected TypeScript input properties explicitly include `| undefined`, and property-level JSDoc must explain analogous semantic distinctions; later included the complete Style read in the initial API, required its independent output snapshot to use readonly TypeScript properties, kept Style input properties mutable, assigned accessor and Proxy behavior to the caller, vouched partial fixed-shape nested input records whose omitted components come from the corresponding Style default rather than stored state, and selected `StyleInput` for the mutable input and `Style` for the readonly output naming direction. The later vouched read-prefix rule names that method `getStyle(node)`. Yunfei subsequently selected the eager plain-object output baseline and included the final reviewed snapshot design in the overall vouch. Detailed derivation and acceptance cases are recorded in [Case 2](binding-cases.md#selected-javascript-container-semantics).

### Numeric closed enums and recommended constants

**Ruling:** Public closed numeric families must use explicit binding-owned integer codes and TypeScript literal unions. Each family must expose one immutable namespace-like constant object whose members are numeric primitives, and the package must export a shared `EnumValue<Family>` type that derives the member union from such an object. Public declarations, documentation, JSDoc, examples, and repository code must use readable named members such as `Display.None` as the recommended form. Passing an equivalent raw numeric literal remains supported but must be described explicitly as not recommended and must not be presented as normal usage. Ordinary type-checked code must accept that raw literal while rejecting an unknown literal code and a widened general `number`. Style input and complete Style output must use the same primitive codes. Tagged-record discriminators must use this same literal-union mechanism so ordinary `===` and `switch` checks narrow their unions without another helper API.

**Limits:** These types are structural rather than branded. TypeScript does not preserve enum-family provenance, so a member from another family is accepted when its numeric literal is also valid in the expected family; runtime code likewise sees only the number. A `const` literal or contextually typed object can use a raw code directly, while a widened `number` variable requires ordinary narrowing or an explicit assertion. This support is a deliberate low-level escape hatch, not a second recommended spelling. Tests may use raw literals to prove the accepted boundary, and documentation may show one only when explaining that boundary and its nonrecommended status. Runtime conversion must still reject every value that is not an exact finite integer member of the expected family before mutation. Numeric values remain visible as numbers in property reads, logs, and JSON. Codes become a stable binding contract once published and must not derive from Taffy's Rust discriminants or declaration order. This ruling defines numeric member and discriminator families, not the outer record needed by a data-carrying variant or an open string vocabulary. Family and member spelling follows the separate vouched naming convention below. The exact code assigned to each member, whether code ranges overlap across families, and whether a shared helper, Rust macro, neutral schema, or generated artifact is the authoritative implementation form remain open. The public declaration must not use a native TypeScript enum or published ambient const enum whose assignment behavior is wider than the selected literal union.

**Why:** Branded numeric intersections reject naked numbers and other families, but compiler tests under TypeScript 5.9 and 7.0 showed that they also prevent ordinary discriminator checks from narrowing the containing union. Requiring an `isVariant` helper would make every tagged-record consumer learn a package-specific control-flow pattern. Literal unions preserve direct numeric conversion, named-member readability, raw literal input, and native TypeScript narrowing while still rejecting unknown literal codes and general `number` values. String values would be more self-describing in logs and serialized data, but Yunfei accepted numeric observability. One shared `EnumValue` type avoids repeating member-union expressions without pretending that TypeScript can verify runtime provenance.

**Source:** Yunfei (`@hyfdev`), 2026-08-11; initially selected branded numeric members so checked TypeScript would reject naked numbers, then revised that choice after compiler evidence showed that branded numeric discriminators do not support ordinary parent-union narrowing and judged an `isVariant` helper unfriendly. He selected ordinary numeric literal unions, retained exported `EnumValue` inference and named constants as the documented and repository-wide recommended form, and accepted direct `0`, `1`, or analogous valid raw literals from users. He then clarified that future documentation must state that passing those literals is not recommended. Detailed derivation and acceptance cases are recorded in [Case 2](binding-cases.md#selected-closed-enum-representation).

### Closed-value family naming

[VOUCHED @hyfdev 2026-08-11]

**Ruling:** A public namespace-like closed-value family must use one singular PascalCase name for both its runtime constant object and its TypeScript type, and every member must use PascalCase. Public uses therefore read as `Display.None`, `Overflow.Hidden`, and `FlexDirection.RowReverse`. Analogous enum-like families added elsewhere in @taffyjs/node must follow the same convention. The API must not uppercase the family or its members and must not append `Value` merely to distinguish the runtime object from the type.

**Limits:** This convention governs scoped enum-like public values. It does not rename externally fixed protocol tokens, compatibility constants whose spelling is itself part of the compatibility contract, error codes, environment variables, or other values that are not members of such a family. A concrete external contract may justify an exception, but the mapping must identify that contract rather than introduce another local style. Acronym normalization within an otherwise PascalCase identifier remains a separate spelling detail when a real member requires it.

**Why:** The family name already communicates the value domain, and TypeScript permits the runtime value and type to share that name. `DisplayValue.None` repeats information, while `DISPLAY.None` or `Display.NONE` applies constant casing despite the existing family scope. PascalCase members match the direct Yoga layout precedent and keep compound terms such as `RowReverse` readable.

**Source:** Yunfei (`@hyfdev`), 2026-08-11; accepted `Display.None` over the uppercase-family, uppercase-member, and `DisplayValue` alternatives, required the same naming style for analogous future cases, and explicitly asked that the convention be vouched.

### Flattened alignment value families

[VOUCHED @hyfdev 2026-08-11]

**Ruling:** The public Style alignment vocabulary must flatten Taffy's named alignment constants into two binding-owned numeric literal families rather than expose strings or `{ keyword, safety }` records. `AlignItems` must contain `Start`, `End`, `FlexStart`, `FlexEnd`, `SelfStart`, `SelfEnd`, `Center`, `Baseline`, `Stretch`, `SafeStart`, `SafeEnd`, `SafeFlexStart`, `SafeFlexEnd`, `SafeSelfStart`, `SafeSelfEnd`, and `SafeCenter`. `AlignContent` must contain `Start`, `End`, `FlexStart`, `FlexEnd`, `Center`, `Stretch`, `SpaceBetween`, `SpaceEvenly`, `SpaceAround`, `SafeStart`, `SafeEnd`, `SafeFlexStart`, `SafeFlexEnd`, and `SafeCenter`. Each family follows the selected numeric-literal and singular-PascalCase rules, and Style input and output use the same primitive members. The `alignItems`, `alignSelf`, `justifyItems`, and `justifySelf` fields use the `AlignItems` value family; `alignContent` and `justifyContent` use `AlignContent`. Their previously selected nullable Style semantics remain unchanged.

**Limits:** The public members are Taffy's named semantic values, not the Cartesian product of its internal keyword and safety fields. Do not expose `SafeBaseline`, `SafeStretch`, `SafeSpaceBetween`, or analogous combinations that CSS does not define and Taffy's parser rejects. An unprefixed positional member represents Taffy's ordinary `Unsafe` safety state; do not add redundant `UnsafeStart` or similar aliases. `SafeStart` remains a distinct round-trippable Style value even though its current layout result equals `Start`, because its overflow fallback is itself. The binding must not derive numeric codes from either internal struct fields or Rust declaration order. Whether additional TypeScript alias names such as `AlignSelf` or `JustifyContent` are useful remains a declaration-surface choice, but a Rust type alias must not create another member set or runtime representation. Same-code values from another family follow the structural limitation of the shared numeric-literal rule. A future Taffy alignment member requires ordinary dependency-upgrade review rather than automatic exposure.

**Why:** Each selected alignment family has a finite public vocabulary, so one primitive member represents the complete semantic value without an object allocation or an invalid keyword-safety combination. Each field's literal union admits only its assigned codes, while readable constants remain the recommended source form. Keeping legal `Safe*` values as explicit members mirrors CSS overflow-position semantics and Taffy's public constants while preserving the same direct numeric input, output, comparison, logging, and JSON behavior selected for other closed families.

### Style scalar floating-point representation

[VOUCHED @hyfdev 2026-08-11]

**Ruling:** A concrete floating-point Style input must accept only a JavaScript `number` and must not coerce strings, booleans, bigints, or other JavaScript values. Because Taffy stores these values as `f32`, the binding must read the JavaScript number as `f64` and explicitly convert it using ordinary floating-point rounding. Exact `f32` representability must not be required. Results outside that domain follow the pinned Taffy behavior and are not separately normalized to match Yoga or CSS. Evidence that a concrete value reaches a Taffy panic or native-safety violation overrides pass-through and requires a safe boundary. Closed-enum codes, integer fields, indices, counts, and collection lengths remain governed by separate exact-integer decisions.

**Why:** JavaScript exposes one `number` type backed by `f64`, while the selected Taffy API computes with and stores `f32`. Accepting ordinary rounding preserves normal JavaScript ergonomics for decimal values and returning the stored value truthfully reflects the value used for layout. Every special JavaScript number also has a defined `f32` representation, so filtering it would add a taffyjs semantic policy rather than make conversion possible. Retaining a separate JavaScript precision copy would add shadow state that can disagree with Taffy and would violate the initial no-data-cache boundary.

### Synchronous measure result and callback failure

[VOUCHED @hyfdev 2026-08-11]

**Ruling:** A measure callback must synchronously return a complete ordinary `SizeInput<number>` with required `width` and `height`; unsupported shapes, missing or incorrectly typed axes, unknown geometry components, and Promise results must produce an ordinary `TypeError`, while every JavaScript number follows the vouched `f64`-to-`f32` pass-through without semantic range validation. ### JavaScript read naming

**Ruling:** Public JavaScript methods that directly read and return one complete or canonical value must consistently use a camelCase `get` prefix, including `getStyle(node)`, `getLayout(node)`, `getParent(node)`, `getChildren(node)`, `getChildCount(node)`, `getChildAtIndex(node, index)`, and `getNodeContext(node)`. Boolean predicates retain their semantic `is` or `has` prefix, such as `isDirty(node)`, rather than becoming `getIsDirty(node)`. Mutations and actions retain their existing verb-led names. This later naming ruling supersedes earlier references to `style(node)`, `layout(node)`, and `nodeContext(node)` without changing those methods' selected behavior.

**Limits:** The `get` prefix does not rename callback argument properties such as `style` and `context`, ordinary object fields, constructors, predicates, mutations, layout computation, or other action methods. The rule fixes the direct-read naming convention and the listed selected methods. Earlier research preferred a separate `queryDomain` form over overloading `getDomain` if a projection API is later justified, but no projection method or reusable naming category is part of the initial API; it requires a separate decision together with its semantics.

**Why:** One direct-accessor convention makes the public tree surface predictable and keeps complete reads visibly paired with mutations such as `setStyle` and `setNodeContext`. Preserving `is` and `has` for predicates avoids awkward names and keeps their boolean role explicit. Deferring projection naming with projection itself avoids treating a research preference as an active public convention.

**Source:** Yunfei (`@hyfdev`), 2026-08-11 and 2026-08-12; explicitly chose and vouched a uniform `get`-prefix style for direct value-reading methods, later explored `queryXxx` for projected reads, and then deferred the projection facility as an optimization outside the initial API. This revision narrows the previously vouched combined naming decision, so the old vouch was removed and no replacement was added automatically.

### Measure invocation and callback-side context mutation

[VOUCHED @hyfdev 2026-08-11]

**Ruling:** A measure callback is a synchronous query controlled by Taffy's traversal and cache, not an exactly-once node event. taffyjs must not promise that every eligible node is called, a fixed invocation count, stable cross-node ordering, or identical constraints across repeated calls. Direct mutation of the exact caller-owned JavaScript context value during a callback remains observable and is neither rolled back nor treated as automatic layout invalidation. Native same-tree operations, including `setNodeContext` and `markDirty`, remain unavailable while the compute is active under the vouched `ERR_TAFFY_TREE_BUSY` rule. If a callback-side mutation changes a node's future measurement semantics, the caller must mark that node dirty after the compute returns.

**Limits:** This is a boundary contract, not a recommendation to make measurement side-effectful. Ordinary callbacks may simply read their inputs and return a size. Measurement-local memoization that does not change the node's semantic measured result does not require invalidation. The public callback JSDoc needs only a compact warning against relying on invocation count, ordering, or automatic invalidation; the decision ledger retains the detailed rationale. The vouched first-failure rule still stops further user callbacks after a callback or result-conversion failure, and this ruling adds no retained callback API, queued same-tree mutation, Proxy tracking, or side-effect rollback. This later ruling resolves the active-callback context-mutation question left open by the earlier node-context entry.

**Why:** Taffy and its cache determine when measurement is needed, while arbitrary JavaScript object changes do not identify which layout dependency changed. Leaving these facts unstated would let a later API derivation accidentally turn the callback into an event contract, disable caching through automatic dirtying, queue same-tree mutations, or promise rollback that the direct binding cannot provide. They are recorded for future API-alignment work rather than elevated into a normal usage ceremony.

**Source:** Yunfei (`@hyfdev`), 2026-08-11; accepted the direct invocation and context-side-effect behavior, explicitly asked that it be vouched, and questioned why it needed emphasis. This entry therefore records it as a future-AI boundary constraint while keeping the user-facing explanation brief.

### Synchronous measurement re-entry

[VOUCHED @hyfdev 2026-08-10]

**Ruling:** A JavaScript measure callback's type must expose only the owned measurement inputs that the callback is allowed to use, and its API documentation must state that native operations on the same TaffyTree are unavailable until the callback returns. If a callback captures that tree and synchronously attempts another native operation, a call that reaches the native access check must throw an ordinary JavaScript `Error` with the stable code `ERR_TAFFY_TREE_BUSY`; it must not silently do nothing or return `undefined`. Its diagnostic message must identify the attempted operation and explain that the same tree cannot be accessed while it is computing layout from a measure callback. The private native class must store `TaffyTree<()>` and any future native state governed by the same access rule behind one `RefCell`, expose shared `&self` napi-rs receivers, and use `try_borrow` or `try_borrow_mut` for every operation instead of relying on napi-rs to protect `&mut self` re-entry. The failed checked borrow must become the controlled JavaScript error rather than a panic. No duplicate JavaScript busy flag is required.

**Limits:** This restriction covers operations that read or mutate the same native tree, including layout reads, style and topology changes, removal, and nested layout computation. NodeId value comparison and use in JavaScript collections do not access the native tree, and a different TaffyTree has independent borrow state and remains usable. JavaScript evaluates argument expressions before entering a method, and wrapper validation or conversion may reject malformed input before the call reaches the native checked borrow; this decision does not add a JavaScript busy precheck or give the re-entry error priority over those earlier failures. This ruling does not decide retained versus per-compute callbacks beyond the selected direct method, callback-result validation, how an exception thrown by the measure callback itself stops an infallible Taffy measure closure, or the native tree's reusable state after such callback failure. A public state getter, `asMutTree`-style access object, or nonthrowing try-access API is not part of the baseline; a later concrete use case may propose one additively without weakening the checked native boundary.

**Why:** Taffy holds exclusive access to its tree throughout `compute_layout_with_measure`, while JavaScript closures can capture the public wrapper and attempt same-tree re-entry. Type declarations and documentation make the intended callback boundary visible but cannot enforce Rust-style borrowing across JavaScript aliases. A single native `RefCell` preserves Rust's access invariant on every actual native entry without duplicating state in JavaScript. Rejecting the invalid call preserves Taffy's semantics. Returning `undefined` from a value-returning method would violate its TypeScript contract, while silently ignoring a void mutation would let layout continue after the caller incorrectly assumes that mutation succeeded; queuing the mutation would instead make the completed layout immediately stale. `ERR_TAFFY_TREE_BUSY` describes the user-visible temporary state without exposing Rust borrowing or re-entry terminology, follows Node.js's stable `error.code` convention, and distinguishes this programming error from unrelated invalid tree states.

**Source:** Yunfei (`@hyfdev`), 2026-08-10; explicitly vouched the restricted callback type, documented same-tree unavailability, controlled synchronous re-entry error rather than silent no-op behavior, native `RefCell` implementation direction, and the `ERR_TAFFY_TREE_BUSY` spelling. The selected code follows Node.js's documented [`error.code` stability convention](https://nodejs.org/api/errors.html#errorcode) and subsystem-specific `ERR_*` naming.

### Case 3 alignment-example conclusion

**Ruling:** Case 3 is complete as an API-alignment example. It establishes that a callback API must be evaluated as one observable sequence covering scheduling and cache reuse, argument and retained-value ownership, active-callback re-entry, successful return conversion, failure transport through the upstream callback type, invalidation, and post-failure state. Later analysis of an equivalent synchronous per-compute callback must reuse that sequence model and the existing Case 2 value rules rather than reopen each callback field independently.

**Limits:** Case 3's concrete internal-zero drain and requested-subtree invalidation belong to Taffy 0.13's synchronous infallible measure closure and cache behavior; they are not a universal callback-error recipe. A retained, asynchronous, off-thread, cancellable, owner-mutating, event-like, natively JavaScript-value-owning, fallible-upstream, differently cached, or transactionally rolled-back callback introduces a new contract and requires fresh analysis. Retained or additional measure APIs do not keep this direct case open. Deferred output-optimization research does not change the complete callback argument or the same-tree busy boundary; another callback data-delivery design remains a separate contract.

**Why:** The case now covers every observable phase of the selected direct measurement flow, while its remaining nearby ideas change callback lifetime, ownership, scheduling, or performance architecture rather than fill a missing answer. Recording both the reusable sequence and its reopen conditions lets a later AI proceed autonomously without copying Taffy-specific failure machinery into a different callback shape.

### ESM-only package entry

[VOUCHED @hyfdev 2026-08-09]

**Ruling:** @taffyjs/node must publish ESM as its only JavaScript module format and must not emit a dedicated CommonJS build.

**Limits:** The napi-rs ESM loader may use createRequire internally to load native addons and optional platform packages; that implementation detail is not a CommonJS public entry. Node.js 22.18 can synchronously require this ESM graph because it has no top-level await, but require(esm) remains release-candidate functionality in that Node release and is not a supported @taffyjs/node contract. This ruling does not decide the broader runtime support matrix. Adding a dedicated CommonJS output requires a new explicit project decision based on a concrete supported-consumer need.

**Why:** ESM is the first-class module system for this package, while CommonJS is secondary and does not justify a separate output. Modern Node.js can already load a synchronous ESM module from require(), so another build would add package and test complexity without changing the primary API.

[VOUCHED @hyfdev 2026-08-10]

**Ruling:** @taffyjs/node must use napi-rs's maintained root-loader distribution model with optional @taffyjs/binding-<platform> packages and must not introduce a generic intermediate binding package or an additional custom loader build without a concrete need.

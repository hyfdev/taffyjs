# Output Optimization Research

This record preserves completed output-materialization research without scheduling an API or implementation. The initial @taffyjs/node boundary remains the complete eager owned snapshot described in [Architecture](architecture.md#complete-owned-snapshots). Lazy snapshots, selective reads, prepared queries, batching, and callback-specific data delivery must not be implemented or extended until a real workload reopens the relevant optimization question.

## Evidence boundary

The exploratory prototypes and their raw benchmark output were not retained as repository artifacts. Their exact timing and memory observations are therefore not durable evidence, are intentionally not recorded as thresholds, and must not support a public performance claim. They suggested only hypotheses for later testing: direct selection can avoid complete conversion work, accessor-backed laziness can add construction and retention cost, and whole-callback laziness helps only when consumers often leave Style unread.

These hypotheses do not identify a consumer bottleneck. They do not show whether direct `getStyle` calls, reads across many nodes, nested Grid data, or Style delivery to actual measure callbacks dominates a real application. Measure callbacks are a potentially repeated conversion path because Taffy controls their invocation and may call a leaf zero, one, or multiple times under traversal and cache behavior, but no workload proves that path is hotter than explicit reads. A tree query also cannot optimize the current callback contract while the same tree is busy; changing callback delivery is a separate API.

## Lazy representations

Accessor-backed and Proxy-backed lazy snapshots were rejected as an initial representation because they add a second object model, hidden first-read work, and retained state without a demonstrated workload need. The unretained prototype suggested that their construction and retention costs could also be material, but that hypothesis requires new durable measurements. A whole-value lazy callback has potential only when consumers often ignore Style and changes the callback contract rather than improving ordinary `getStyle`.

This finding does not impose a permanent ban. Reconsidering laziness requires a workload that complete snapshots and a more targeted additive optimization cannot serve, plus new measurements covering construction, consumed reads, retention, garbage collection, and callback behavior.

## Selective-read designs investigated

The first complete design used camelCase string paths with dot property segments and bracketed integer indices, accepted one path or an ordered path array, and returned an exact value or readonly tuple. Its custom distributive TypeScript resolver was intended to keep a tagged-union branch-only path as `T | undefined`, preserve `null` when selecting a nullable field itself, return `undefined` when descending through `null` or an inactive branch, and preserve ordinary narrowing when selecting the complete tagged record. The exploratory work encountered a general-purpose `Get` result that became `unknown` for an absent union branch; because the exact fixture was not retained, a future design must reproduce these cases against any candidate helper rather than treat that observation as current library evidence. The design also exposed maintenance obligations: a public path grammar, recursive type computation and depth policy, runtime parsing, Rust schema dispatch, and parity tests must evolve together.

A later unretained builder prototype replaced path strings with typed `.get(field).index(number)` cursors. It explored hidden domain brands, distributive lookup across unions and nullable values, dynamic numeric indices, and exact results for a single selection or readonly selection tuple. Any reopened design must reproduce and retain declaration fixtures for two easy-to-miss soundness constraints: nonapplicable branches of an array-or-record union contribute `undefined`, and tuple index unions distribute so a valid-or-out-of-bounds index does not collapse to only `undefined`.

The unretained native prototype suggested that compiling a typed selection plan on every read can dominate a small query, while reusing an already prepared native plan can reduce planning overhead. This is a design hypothesis, not performance evidence. If a real workload later justifies deep queries, a prepared design is one candidate: execute the builder once, validate every path against the complete public schema, compile owned typed selectors, and reuse the opaque query across nodes and trees in the same package instance. Dynamic indices would be captured at creation and require rebuilding or caller caching when they change. The reopened work must retain its implementation, commands, raw results, and end-to-end measurements before using performance to choose this architecture.

That candidate still requires substantial machinery. The authored wrapper must keep the raw native handle in a module-private `WeakMap` or equivalent unforgeable boundary rather than trust a public TypeScript brand or arbitrary N-API external. TypeScript schema, Rust selector compilation, and full, subtree, and leaf converters require an exhaustive mechanically checked parity inventory from the first domain. Named result projections, collection traversal, filters, slices, wildcard selection, array-length operators, and a general data-processing DSL were not justified. The investigation considered optics, JSON Pointer, JSONPath, GraphQL, and form-path approaches but selected none for the closed TypeScript schema and Rust execution boundary; a reopened design must reevaluate the then-current ecosystem rather than assume that conclusion remains true.

## Other candidates

A top-level-key query is a smaller possible optimization: one `keyof Style` or a readonly key tuple could select complete top-level fields without a deep path grammar or recursive selector system. It may be sufficient when callers need scalars or small records, but it can retain most conversion cost when the selected field is a large Grid collection. It is a candidate, not a promised first step.

Batch reads may matter more when a consumer crosses Node-API once per node. Callback-specific omission or selection may matter more when actual measure invocations dominate. `DetailedLayoutInfo`, if it is ever exposed, is the closest additional closed snapshot candidate because its Grid branch contains nested track and item vectors; `Layout` is a weaker candidate because it is fixed-size but may still allocate several JavaScript records across many nodes. Topology operations, small geometry values, scalar state, and JavaScript-owned node context do not justify a generic snapshot query.

The earlier naming study preferred a separate `queryDomain` operation over overloading a complete `getDomain` or appending `Selectively`, and preferred one operation accepting single and multiple selections over singular and plural method names. This remains research context rather than a method on the initial API; no query grammar, lifecycle, result shape, or public type is currently selected.

## Reopen conditions

Do not reopen output optimization from a microbenchmark alone. First identify a consumer workload and measure which cost dominates: complete conversion, nested collection conversion, repeated Node-API calls, retained output memory, or callback delivery. Then choose the smallest API that addresses that cost rather than assuming deep queries, top-level keys, batching, or callback selection is the universal progression.

A selectable domain must be binding-owned and closed, have multiple meaningful nested projections that direct getters cannot express more clearly, retain a useful complete getter, show material full-conversion cost in the target workload, and permit direct native selection without a new live-borrow or side-effect model. Arbitrary JavaScript-owned context remains opaque. Any reopened design must keep complete getters unchanged, distinguish `null` from missing selection results, preserve tagged-union soundness, validate every plan before native execution, reuse canonical converters, and establish schema parity tests before publication.
